# 发布链路性能分析与优化

本轮分析围绕手机编辑后的本地发布准备过程：源文件哈希扫描、输入快照、Markdown/HTML 转换、静态页面输出和资产清单。测量没有修改真实笔记，也没有向 Cloudflare 发布测试内容。

## 测量方法

环境为 Node.js v26.12.1、Intel Core i9-13980HX、Linux 本地文件系统。对照版本为 `e5161c5`，通过独立工作目录运行相同基准脚本，并复制同一份真实笔记；旧编译器只增加了等待初始化完成的 `ready()` 方法，没有改变业务逻辑。前后均复用同一份依赖版本。

两组样本：

- 当前 Vault：20 篇 Markdown，其中 18 篇可发布。
- 扩展样本：250 篇生成的 Markdown，每篇包含标题、格式和双向链接。

每组从独立空状态目录开始，进行一次冷构建、一次无修改的缓存命中构建，以及 5 次同日正文末尾的小改，更新耗时取中位数。脚本在临时目录复制笔记，保留文件时间；不使用真实发布状态目录。

表中的总耗时包含两次完整哈希扫描、快照复制、编译和输出清单计算；不包含进程/插件初始化、临时测试数据生成、快照清理、LiveSync 同步、编辑合并等待或 Cloudflare 部署。基准会强制生成快照以观察缓存；实际 watch 在源哈希未变化时会直接跳过构建。

运行当前版本：

```bash
pnpm static:bench --skip-og --edits=5 --output=/tmp/quartz-real.json
pnpm static:bench --notes=250 --skip-og --edits=5 --output=/tmp/quartz-scale.json
```

采集 CPU profile（输出到 `/tmp`，可在 Chrome DevTools 的 Performance 面板加载）：

```bash
node --cpu-prof --cpu-prof-dir=/tmp scripts/benchmark-static.mjs --edits=1
```

## 热点与处理

**可选分享图。** 初次 CPU 采样中，最热函数是字体解析的 `parseCmapTableFormat12`。启用 OG 时一次真实笔记冷构建约 7.95 秒，其中约 6.98 秒消耗在 OG 输出；磁盘缓存中的两份 CJK 字体合计约 21 MiB。根据使用需求，本轮直接禁用 OG 插件，不继续优化字体读取与渲染。默认分享图 `static/og-image.png` 保留。

这属于关闭可选功能，不算作相同功能下的算法加速。下面的代码对照测试前后均关闭 OG，避免混算。

**文件 I/O 串行。** 扫描、快照复制、完整性复核和资产清单原先逐文件串行 await。改为最多 4 个文件操作并行，结果仍按排序后的文件路径组织，因此哈希清单不会受到任务完成顺序影响。全部文件仍计算内容哈希，没有改为只信任 mtime/size。

失败时先等待所有已启动的文件操作结束，再抛出异常，防止调用方清理目录后仍有后台写入。并发数固定为 4，限制文件句柄及同时驻留的大文件缓冲区。

**SQLite 缓存写入。** 原实现每个缓存项重新准备 SQL，并独立自动提交。现在复用 prepared statements，将一次 Markdown/HTML 阶段的缓存写入放进事务；解析失败会回滚，后续构建可正常恢复。渲染使用的 AST 仍从 JSON 还原，保留隔离，避免转引和组件修改污染缓存。

**无效 HTML 变化。** 上游目录组件的全局递增计数器会把 `toc-0` 变为 `toc-7` 等值，使内容不变的页面也改变哈希。新增小型本地适配 `plugins/stable-toc`，保留原转换器、布局和样式，使用 Preact `useId()`；同时修正列表覆盖传入 ID 导致 `aria-controls` 与目标不匹配的问题。此适配使用主仓库已有的 en-US/zh-CN 翻译，并保留上游 MIT 许可及来源说明。

**可观测性。** 编译器和发布日志新增阶段、输出插件及 I/O 计时，基准记录实际发生变化的文件集合，后续可以区分解析、渲染、扫描和上传瓶颈。

## 同功能对照结果

两侧均关闭 OG，单位为毫秒；冷构建与无修改构建为单次样本，单篇更新为 5 次样本中位数。墙钟时间会受调度和文件缓存影响，这些数值不是时延承诺。

| 样本与场景               | 优化前 | 优化后 | 降幅 |
| ------------------------ | -----: | -----: | ---: |
| 真实笔记，冷构建         |  919.7 |  529.0 |  42% |
| 真实笔记，无修改构建     |  297.6 |  158.6 |  47% |
| 真实笔记，单篇更新中位数 |  287.7 |  169.8 |  41% |
| 250 篇，冷构建           | 3684.2 | 2181.7 |  41% |
| 250 篇，无修改构建       | 1210.2 |  798.5 |  34% |
| 250 篇，单篇更新中位数   | 1034.3 |  630.9 |  39% |

单篇更新中，扫描、复制、复核和清单合计的 I/O 中位数：

| 样本     | 优化前 | 优化后 |
| -------- | -----: | -----: |
| 真实笔记 |  103.6 |   23.2 |
| 250 篇   |  387.5 |   61.3 |

真实笔记无修改时，变化的资产从 7 个 HTML 降到 0；本次正文末尾小改从 8 个文件降到 2 个（文章 HTML 和搜索索引）。这减少了无关上传，也让部署队列的相同快照去重可靠生效。修改标题、标签、日期或被转引内容时，受影响文件集合可能更大，不能一概承诺只上传两个文件。

## 保留的边界与下一步

仍采用增量解析加完整输出快照，未对未知插件尝试不完整的页面依赖失效。扩展样本更新时，页面输出仍约占编译耗时的七成，是本地后续优化的主要方向；进一步缓存页面需要覆盖转引、别名、目录、反向链接、插件全局元数据及配置依赖。

本轮没有改变 Cloudflare 发布流程、编辑合并等待或缓存策略。之前实测的远端版本发布仍需数秒，已经比当前小站的本地更新准备耗时更长；不能把本地 170 ms 理解为手机到线上只需 170 ms。

静态体积检查中，最大的单个 JS 约 75 KiB（gzip 约 26 KiB），核心 CSS 约 61 KiB（gzip 约 11 KiB）；favicon 原图约 138 KiB，存在进一步压缩空间。本轮未修改图片外观，也未把资产体积检查当作浏览器加载性能或 Lighthouse 测试结果。

回归验证覆盖：无修改产物哈希一致、目录按钮目标 ID、转引更新、别名移除、草稿/隐藏文章、删除/重命名、缓存事务失败恢复、文件并发失败清理、监听重试、部署队列串行及快照完整性。
